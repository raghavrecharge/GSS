# SaaS architecture mapper

## Boundaries
This skill maps observable behaviour; it cannot reveal hidden server internals. Inspect only:
- public technical documentation;
- normal browser requests generated by authorized user interactions;
- schemas or source code supplied by the user;
- test environments and accounts explicitly authorized by the user.

Do not scan, fuzz, enumerate, exploit, or bypass endpoints. Do not extract private customer data, secrets, tokens, or production database contents.

## Procedure

### 1. Identify the visible system boundary
Document:
- browser client and visible framework clues (as hypotheses unless directly verified);
- authentication flow as observed;
- user-visible modules and roles;
- third-party services explicitly visible in UI or documentation;
- file, email, payment, analytics, and notification workflows;
- offline, retry, and failure behaviour.

### 2. Observe normal API behaviour
When network inspection is authorized:
- trigger a normal UI action;
- record method, path pattern, request purpose, sanitized shape, response status, and visible effect;
- redact authorization headers, cookies, tokens, personal data, and identifiers;
- never replay requests that mutate production state;
- distinguish observed request/response shape from inferred contract.

### 3. Derive domain model
For each entity, document:
- purpose;
- fields needed by the observed workflows;
- relationships and cardinality;
- lifecycle/status transitions;
- tenant ownership;
- access rules;
- retention/deletion considerations.

Use synthetic examples. Do not copy live user records.

### 4. Design independent API contracts
Define:
- resource and action;
- HTTP method and route;
- authentication and authorization;
- request schema and validation;
- response schema;
- status/error codes;
- pagination, filtering, sorting;
- idempotency and concurrency behaviour for writes;
- audit events for sensitive operations.

Prefer consistent REST or the repository's existing API style. Avoid pretending the reference's internal API is known.

### 5. Security and tenancy
Specify:
- authentication/session strategy;
- role- and resource-level authorization;
- tenant isolation;
- server-side input validation;
- CSRF/CORS policy where applicable;
- rate limiting and abuse controls;
- secure file upload/download;
- secret management;
- audit logging without sensitive payloads;
- backup, deletion, and retention requirements.

Never trust frontend-only permission checks.

### 6. Produce architecture artifacts
- `architecture.md`: components, boundaries, flows, deployment assumptions.
- `api-contract.md`: endpoint contracts and error conventions.
- `data-model.md`: entities, relationships, constraints, indexes.
- `security-and-permissions.md`: roles, ownership, tenant isolation, controls.

## Confidence labels
- Observed: directly visible in permitted evidence.
- Inferred: plausible technical explanation; include confidence and alternatives.
- Proposed: independent implementation choice.
- Unknown: not discoverable from current scope.

## Review
Check that every critical feature maps to a proposed API/data operation and that every write operation has authorization, validation, error handling, and tests.
